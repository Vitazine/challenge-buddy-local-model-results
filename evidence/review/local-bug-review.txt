Приоритет P1: существующий допустимый пользовательский сценарий блокируется.

2. P1 — последний добавленный тест ломает typecheck конечной версии.
   tests/api-startdate-validation.test.ts:25 использует (err as Error).statusCode. Стандартный Error не имеет statusCode; нужное поле существует у AppError, однако соответствующий тип здесь не импортируется/не сужается. Это TS2339 при полном check, даже несмотря на прежний PASS кандидата 06: тогда файла ещё не было. Фактический compiler в этом Review не запускался, вывод из строгого TypeScript и конечного кода. Критерий: существующие проверки должны пройти на последней версии, небезопасные приведения не добавлять.

3. P2 — тест воспроизведения проглатывает собственный assert.fail и проходит при сломанном сервере.
   tests/day04-defect-reproduction.test.ts:19-24: если service.create не бросит ошибку, assert.fail бросит AssertionError с текстом «Сервер должен отклонить startDate ...»; catch принимает Error и regex, в который входит startDate. Поэтому тест станет зелёным именно при принятии запрещённой даты. Это не гипотеза: checks/03-test.stdout.log показывает PASS 16/16 на кандидате 02 до первого изменения server/challenges.ts (первое изменение сервера — step 9, после check на step 8).
   Отдельно tests/domain.test.ts:108-115: собственный assert.fail с «Дата сегодня + 8 дней должна быть отклонена» НЕ содержит «дата старта» или startDate, поэтому его catch НЕ проглотит собственный fail. Этот domain-тест способен обнаружить отсутствие server throw. При этом он не проверяет тип/statusCode исключения и отсутствие INSERT. Дефект ложного PASS относится к repro, а не ко всем try/catch тестам.
   Критерий профиля Bug Fix: содержательная регрессия, проверка наблюдаемого поведения и корректное воспроизведение. Блокирует доверие к repro, а не доказывает неверность конечного серверного guard.

4. P2 — заявленный тест обхода формы не тестирует HTTP API; отсутствие записи при отказе не проверено ни одним новым тестом.
   tests/api-startdate-validation.test.ts:7 назван «API ... via direct POST», но на строках 8-22 создаёт repository/service и вызывает service.create. buildApp/app.inject/fetch отсутствуют; route, входная схема, auth, HTTP status/body этим тестом не проходят. Название и комментарий не являются доказательством POST. Ни этот файл, ни domain-тест +8, ни repro не проверяют count/list или фактические строки БД после отказа. Они могут пройти при нежелательной записи перед throw. Критерий TASK: прямой POST в обход формы и отсутствие записи при отказе; профиль: содержательные проверки границ и последствий. Независимая проверка оркестратора может подтвердить продукт, но не исправляет недостаток сгенерированных тестов.

5. P2 — новый тест прошлой даты зависит от реального дня при фиксированных часах сервиса.
   tests/domain.test.ts:145 внедряет now=2026-10-24T10:00:00Z (tests/helpers.ts:4), но строка 148 вызывает todayInZone("UTC") без now. Например, при запуске 2026-11-02 вычислится pastDate=2026-11-01, который больше фиксированной серверной границы 2026-10-31; тест «past dates still allowed» упадёт на корректном guard. Критерий TASK/профиля: использовать переданные часы для воспроизводимых календарных проверок. Repro тоже использует реальные часы, но совпадение его двух часов дополнительно маскируется дефектом 3.
